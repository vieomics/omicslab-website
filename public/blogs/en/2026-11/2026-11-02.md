## A full run, with nothing to install

We kept the `test_full` profile of `nf-core/bacass` — the configuration used to exercise the whole short-read workflow: quality control, adapter trimming, contamination screening, assembly, annotation and reporting — and replaced its default samplesheet with one public run from ENA project [PRJEB86571](https://www.ebi.ac.uk/ena/browser/view/PRJEB86571). This is the dataset behind our [blaNDM article](/en/blogs/bla-ndm-on-omicslab); the run used here is `ERR14693665` (isolate `021-A-244`).

The result:

- **19 minutes** of job runtime, as shown in the job overview.
- **16 CPUs, 32 GB RAM and 100 GB of disk** on GreenNode HCM.
- **3,184 VND**, made up of 2,841 VND for cloud compute and 343 VND for the platform fee.
- No Nextflow install, no containers, no terminal, no HPC cluster.
- The input was a TSV file of a few hundred bytes; the reads and reference databases were already in the public workspace.

This was a validation run on public data, not a benchmark for every dataset. Runtime and cost vary with data size, machine configuration and infrastructure region; the figures below belong to this run.

## Why run the full profile?

`nf-core/bacass` ships with several profiles. The `test` profile is very small and fast, useful for checking that the pipeline works. The `test_full` profile runs every step on larger data and is closer to a real analysis. For a new user, it is a way to see what the pipeline does before trusting it with their own data.

We used **one sample** rather than the two in the default sheet. One sample is enough to walk through every step and keeps the run short; adding rows later is straightforward. The pipeline steps do not change.

If you want the concepts behind nf-core, Nextflow and containers first, read [How to Run nf-core Pipelines on the Omicslab Platform](/en/blogs/how-to-run-nf-core-pipelines-on-omicslab). This post is about the doing.

## Before you start

You need three things:

1. **An account** at [platform.omicslab.io](https://platform.omicslab.io). Sign-up does not require a card; you pay when you run an analysis. The steps are in the [platform guide, Chapter 01](/en/guide#bat-dau-dang-nhap).
2. **A workspace** — where data, pipelines and run history live.
3. **A samplesheet** — a TSV table describing which sample uses which read files.

For this run, the `PRJEB86571` reads were already in Omicslab's public workspace. We did not upload FASTQ files; we created a small TSV that points at reads that were already there. That is why preparation took minutes rather than hours.

## Step 1 — Get the test_full samplesheet

The `test_full` profile points to a sample sheet in the `nf-core/test-datasets` repository: [bacass_full.tsv](https://raw.githubusercontent.com/nf-core/test-datasets/bacass/bacass_full.tsv). The sheet has two rows, one per public read set:

| ID | R1 | R2 | LongFastQ | Fast5 | GenomeSize |
| --- | --- | --- | --- | --- | --- |
| `SRR8482585` | `…/SRR8482585_1.fastq.gz` | `…/SRR8482585_2.fastq.gz` | `NA` | `NA` | `NA` |
| `SRR10093029` | `…/SRR10093029_1.fastq.gz` | `…/SRR10093029_2.fastq.gz` | `NA` | `NA` | `NA` |

*Table 1 — The two sample rows in `bacass_full.tsv`. Full paths are in the source file; they are shortened here. For short-read data, `LongFastQ` and `Fast5` stay `NA`. We kept one row and replaced it with the run from PRJEB86571.*

You do not have to use those two samples. What matters is the **column structure**: `ID`, `R1`, `R2`, `LongFastQ`, `Fast5`, `GenomeSize`. For short reads, `LongFastQ` and `Fast5` stay `NA`.

## Step 2 — Build a one-row samplesheet in the browser

Upload the TSV to the workspace, then open it in the platform's table editor:

![Uploading the samplesheet to the workspace](./imgs/upload-samplesheet.png)

*Figure 1 — Uploading the TSV to the workspace. The sample file is a few hundred bytes; no FASTQ is uploaded at this stage.*

![Editing the samplesheet in the browser](./imgs/edit-samplesheet.png)

*Figure 2 — The samplesheet opens as a table. Rows can be removed, sample names changed and `R1`/`R2` paths replaced without Excel.*

We kept one row, changed the `ID` to the sample label we wanted, then pointed `R1` and `R2` at two FASTQ files in the public workspace:

![Choosing reads from the Omicslab public workspace](./imgs/choose-public-reads.png)

*Figure 3 — The file picker opens the public `Omicslab → datasets → PRJEB86571` workspace. `R1` is selected here; `R2` follows. The reads do not need to be downloaded to a laptop.*

After saving, the sheet has one row and two paths starting with `s3://...`. That is an address inside the platform's data store, not a command to type:

![The one-row samplesheet is ready](./imgs/samplesheet-ready.png)

*Figure 4 — The finished samplesheet: one sample, `R1` and `R2` pointing at reads in the workspace. This file is the entire data-preparation step.*

:::tip
If your data is on your own machine, upload the FASTQ files to the workspace first and choose them in the same dialog. For public datasets already in the workspace, point the samplesheet at the existing paths.
:::

## Step 3 — Choose the pipeline, version and profile

Open **Analysis → Tools** and find `nf-core/bacass`:

![Choosing nf-core/bacass from the tool catalogue](./imgs/bacass-catalog.png)

*Figure 5 — `nf-core/bacass` sits in the workspace tool catalogue alongside other nf-core pipelines.*

In the run configuration, choose:

- **Tag** `2.6.1` — the pipeline version to run.
- **Profile** `test_full` — the full short-read configuration.

![Choosing version 2.6.1 and the test_full profile](./imgs/bacass-test-full.png)

*Figure 6 — Version `2.6.1` and profile `test_full`. Both are recorded in the manifest, so the run can be reproduced.*

The platform reads the pipeline schema and builds the parameter form. You do not need to remember parameter names or type commands; choose the version, the profile and the input file.

## Step 4 — Point input at the samplesheet

Open **Input/output options** and select the samplesheet you created. Keep the default `outdir` (`data/bacass/$job_id`) and leave the email field empty unless you want a completion summary:

![Pointing input at the samplesheet and keeping the defaults](./imgs/run-input-parameters.png)

*Figure 7 — `input` points at the one-row samplesheet; `outdir` keeps the default. The remaining parameters stay as they are for a first run.*

The tabs on the left (`QC and Trim`, `Assembly parameters`, `BUSCO options`, `Annotation` and others) let you change parameters when needed. For a validation run, the defaults are enough. Anything you change is recorded in the manifest.

## Step 5 — Use the prepared reference databases

`nf-core/bacass` uses Kraken2 and KmerFinder for contamination screening. Both databases are large; downloading them from AWS or Zenodo can take longer than the assembly itself.

For this run, we selected the copies already in Omicslab's public workspace:

![Choosing the Kraken2 and KmerFinder databases from the workspace](./imgs/prestaged-databases.png)

*Figure 8 — `kraken2db` and `kmerfinderdb` point at copies prepared in the workspace instead of remote download URLs. In this run, the databases sat next to the compute.*

This is one practical difference of running on the platform: reference data and compute are in the same place, so the job does not wait for a 30 GB download before it starts. If your pipeline needs a different database, point it at your own copy or ask support.

## Step 6 — Review the manifest, choose compute and run

Choose compute in the **Compute** tab. For this run: GreenNode HCM, 16 CPUs, 32 GB RAM and 100 GB of disk. The form showed an estimate of **9,284 VND** for a one-hour ceiling; the final charge depends on actual runtime.

Name the manifest so it is easy to find later, then press **Run**:

![Reviewing the manifest, naming it and running](./imgs/manifest-and-estimate.png)

*Figure 9 — The manifest records every parameter, the pipeline version and the resources. We named it `test_full_from_scratch.omxa.json` and pressed Run. There is no JSON to edit.*

The manifest is the full record of the run. Keeping it is the simplest way to reproduce a result or compare two pipeline versions.

## Step 7 — Watch the job

The log streams in the browser. At the top you see the pipeline version, the input path and the steps as they run. There is no terminal to open and no separate cluster to monitor.

![Job log: data and databases staged from the workspace](./imgs/data-staged-in-vietnam.png)

*Figure 10 — The log shows reads from `PRJEB86571` and the two databases being staged into the job from the workspace. In this run, the data was served from the platform's storage in Vietnam.*

The Apptainer images for the pipeline were also prepared by Omicslab, so the job did not have to pull images from an international registry. You can close the tab; the job keeps running and you can return later.

## Step 8 — Read the results

When the job finishes, open the `outdir` folder in **Data**. The results are grouped by tool:

![The nf-core/bacass results folder](./imgs/results-folder.png)

*Figure 11 — The output includes FastQC, Kmerfinder, Kraken2, Prokka, QUAST, Unicycler, busco, multiqc, pipeline_info and trimming.*

A quick reading guide:

| Folder | What it contains |
| --- | --- |
| `FastQC`, `trimming` | Read quality before and after adapter trimming |
| `Kraken2`, `Kmerfinder` | Contamination and species checks |
| `Unicycler` | The genome assembly |
| `Prokka` | Gene annotation |
| `QUAST`, `busco` | Assembly quality and completeness |
| `multiqc` | A single HTML summary report |
| `pipeline_info` | Pipeline and tool versions, plus the execution report |

Open `multiqc/multiqc_report.html` directly in the browser:

![MultiQC opened directly in the browser](./imgs/multiqc-inline.png)

*Figure 12 — MultiQC opens in the browser, with nothing to download or install. The charts can be zoomed for reading.*

If you need the results on your own machine, select the folder and download it; the platform packages it as a zip:

![Downloading the results folder](./imgs/download-results-zip.png)

*Figure 13 — Select the results folder and download it. For one sample, the FastQC folder is a few MB; the full output depends on the pipeline.*

## Step 9 — Rerun from the saved manifest

The manifest is stored under **Data → nf-core/bacass → 2.6.1**. From there you can launch the same configuration again:

![Rerunning from a saved manifest](./imgs/reuse-manifest.png)

*Figure 14 — This run's manifest sits beside older manifests. Use the launch icon to reopen the configuration, then replace the samplesheet if needed.*

For a new batch, replace the samplesheet and keep the rest. This is how a group can standardise one workflow across many datasets without rebuilding the configuration each time.

**16 CPUs and 32 GB RAM, rented for 19 minutes, for 3,184 VND.** That is the shape of a workstation or a small HPC node; the difference is that you pay only for the time the job runs, not for the machine or the cluster around it.

The form showed 9,284 VND before the run, based on a one-hour ceiling. The job finished in 19 minutes, so the actual charge was 3,184 VND. This is the price of this run, at this time, with this configuration; it is not a quote for every dataset.

`nf-core/bacass` is open source and carries no licence fee. You pay for compute and storage.

## What this means for a new user

A first full-profile run is often the hardest part of learning nf-core: installing Nextflow, setting up containers, choosing a profile, downloading databases and arranging resources. On the platform, those parts sit behind one form. What remains is preparing the samplesheet and reading the output.

For a research group, the same manifest can be used to:

- **Validate a pipeline before running real data** — confirm that it works with your input.
- **Compare versions** — rerun the same data with another tag and compare the output.
- **Teach** — show the whole workflow without building an environment.
- **Standardise a workflow** — change only the samplesheet for each new batch.

This was a validation run on public data, not a clinical workflow. For human or clinical data, check the service scope and the legal requirements before uploading anything to the public platform.
