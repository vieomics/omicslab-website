:::info
We demonstrate a config-driven pipeline that filters, fetches, auto-curates, and harmonizes clinical metadata from NCBI GEO into standardized cancer cohorts, starting with a breast cancer cohort (BRCA-mini) with treatment and survival endpoints.
:::

Public omics data repositories like NCBI GEO hold millions of datasets with rich clinical annotations. However, leveraging this data for large-scale meta-analysis is hindered by several challenges:

- **Inconsistent metadata**: Column names and value encodings vary wildly across studies (e.g., `er_status`, `ER Status`, `estrogen_receptor`, `ER_IHC` all mean the same thing).
- **Noisy annotations**: Studies often mix clinical, technical, and administrative metadata in unstructured formats.
- **Scale mismatch**: GEO hosts 8M+ samples across thousands of studies — fully manual curation does not scale. Using AI fully does not perfectly solve the complex datasets.
- **Relevance filtering**: Finding studies with both treatment information and survival outcomes requires domain-specific filtering.

To address these challenges, we built a modular, config-driven data curation and harmonization pipeline backed by OmicIDX — a cloud-native replacement for SRAdb/GEOmetadb that indexes 80M+ SRA runs and 8M+ GEO samples into queryable DuckDB Parquet files.

## Pipeline Stages

### Stage 1: Dataset Filtering

The entry point is a cohort-specific Python script that queries OmicIDX Parquet files via DuckDB to identify relevant GEO studies. For BRCA-mini, this filters for:

- Studies matching breast cancer regex patterns (BRCA, TNBC, mammary carcinoma, etc.)
- Human samples with ≥200 patients
- Contains both treatment and survival keywords in the study description
- Excludes cell-line, xenograft, and in vitro models

This produces `gse_ids.txt` — a focused list of 785 GSE accessions suitable for meta-analysis.

### Stage 2: Metadata Fetching

Two generic scripts consume the filtered GSE list:

**`fetch_platforms.py`** — Resolves platform accession, technology, and manufacturer for each GSE from the OmicIDX Parquet store. Outputs `gse_platforms.csv` with platform frequency summaries across the cohort.

**`fetch_clinical.py`** — Downloads raw clinical metadata for all GSM samples in each GSE, writing per-study CSV files (`<GSE>_clinical.csv`). Uses DuckDB's HTTPFS extension to query remote Parquet files directly without local downloads.

### Stage 3: Curation

Curation transforms raw, inconsistent column names and values into a standardized format. The pipeline supports two paths:

**LLM Auto-Curation** (`agent_curate.py`): Each dataset's columns are sent to GPT-4o-mini with the schema context. The LLM maps raw column names to target variables (e.g., `days_to_death` → `os_time_months`) and normalizes categorical values (e.g., `positive/negative`, `1/0`, `yes/no` → unified mappings). Results are cached to avoid redundant API calls.

**Interactive Review UI** (`curation_app.py`): A Streamlit-based dashboard with two pages:

- **Overview & Progress**: KPIs (datasets, samples, treatment/survival counts), omics type distribution charts, platform usage, and curation progress tracking with approve/re-review/remove counts.
- **Review Board**: Side-by-side before/after preview for each curated dataset, showing which columns were mapped, how values were transformed, and providing one-click approve/re-review/remove actions.

### Stage 4: Harmonization

The `harmonize.py` script applies column name mappings and value transformations to produce standardized output datasets. Given a `column_mappings.json` (generated during curation), it:

- Renames columns to schema variable names
- Normalizes categorical values using regex patterns defined in the schema YAML
- Converts units (days → months, cm → mm) via post-processing rules
- Validates types (numeric fields contain only numbers, binary events contain only 0/1/FALSE/TRUE)

### Stage 5: Summarization

Automated quality reports provide:

- Per-variable coverage statistics (% of datasets with each harmonized variable)
- Distributions of categorical variables across the cohort
- Platform and omics type summaries
- Data completeness heatmaps

## The Standardized Schema

Each cancer type defines a YAML schema with variable groups. The BRCA schema covers:

| Group                 | Variables                                                                 |
| --------------------- | ------------------------------------------------------------------------- |
| Receptor Status       | ER, PR, HER2 status                                                       |
| Survival Endpoints    | OS, DFS, DMFS, RFS (event + time in months)                               |
| Tumor Characteristics | Histological grade, tumor size (mm), AJCC/T/N/M stage, lymph node status  |
| Treatment             | Chemotherapy, hormone therapy, radiotherapy, pathologic complete response |
| Demographics          | Age at diagnosis, menopausal status, gender                               |
| Molecular             | PAM50 subtype, Ki67 proliferation index                                   |
| Other                 | Histological type, p53 status, tissue origin                              |

## OmicIDX: The Data Backend

Underpinning the curation pipeline is OmicIDX, a cloud-native replacement for the legacy SRAdb and GEOmetadb. It comprises:

- **Parsers** (`omicidx-parsers`): Type-safe XML/SOFT format parsers for NCBI SRA, GEO, BioSample, and PubMed, producing Pydantic v2 models.
- **ETL** (`omicidx-etl`): Extract-transform-load pipelines that convert raw NCBI data to partitioned Parquet files on S3-compatible storage (Cloudflare R2), accessible via DuckDB with HTTPFS.
- **API** (`omicidx-api`): Read-only FastAPI REST API deployed at `api-omicidx.cancerdatasci.org` with keyset cursor pagination and consistent response envelopes.
- **Orchestrator** (`omicidx-dagster`): Dagster assets scheduling daily ETL runs, syncing to both DuckDB (for querying) and PostgreSQL (for the API).

This architecture enables querying 80M+ SRA runs and 8M+ GEO samples in milliseconds using local DuckDB, without requiring a running database server — ideal for offline and reproducible research workflows.

## Quick Start

### Prerequisites

```bash
git clone --recursive https://github.com/omicslab/omicslab-datasets.git
cd omicslab-datasets
pixi shell
```

### Run the Full BRCA-mini Pipeline

```bash
# 1. Filter datasets for breast cancer (cohort-specific)
pixi run python cohorts/BRCA-mini/scripts/filtering_datasets.py \
    --parquet-dir cohorts/BRCA-mini/parquet \
    --output cohorts/BRCA-mini/datasets/gse_ids.txt

# 2. Fetch platform and clinical data
pixi run python apps/fetch_platforms.py \
    --parquet-dir cohorts/BRCA-mini/parquet \
    --gse-ids cohorts/BRCA-mini/datasets/gse_ids.txt \
    --output-dir cohorts/BRCA-mini/datasets/raw

pixi run python apps/fetch_clinical.py \
    -i cohorts/BRCA-mini/datasets/gse_ids.txt \
    -o cohorts/BRCA-mini/datasets/raw \
    --parquet-dir cohorts/BRCA-mini/parquet

# 3. LLM auto-curation (requires OPENAI_API_KEY)
pixi run python apps/agent_curate.py BRCA-mini

# 4. Launch interactive curation review UI
pixi run streamlit run apps/curation_app.py -- \
    --raw-dir cohorts/BRCA-mini/datasets/raw \
    --curated-dir cohorts/BRCA-mini/datasets/curated_json \
    --output-dir cohorts/BRCA-mini/output/json
```

### Adding a New Cancer Type

To add support for a new cancer type (e.g., LUAD):

1. Add a new entry in `cohorts/cancers.yaml` with regex patterns for cancer type, treatment keywords, survival keywords, and exclusion patterns.
2. Create `cohorts/LUAD/config/luad_schema.yaml` defining target variables and value mappings.
3. Create `cohorts/LUAD/scripts/filtering_datasets.py` with the LUAD-specific regex filters.
4. Run the same generic pipeline steps — all other scripts are cancer-agnostic.
