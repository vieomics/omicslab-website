Trong [Phần 1](/blogs/how-to-version-control-git-bioinformatics-part-1) của loạt bài này, chúng ta đã xem những kiến thức cơ bản của Git, cách tạo nhánh và quy trình cộng tác. Ở bài này, chúng ta tiếp tục với dự án nhỏ đó và thêm một lớp tự động hoá: một Makefile tải dữ liệu kiểm thử và chạy pipeline, một bài kiểm thử end-to-end, và một workflow GitHub Actions.

Continuous integration (CI) và continuous delivery (CD) là những thuật ngữ vay mượn từ phát triển phần mềm. Khi áp dụng cho một kho bioinformatics, chúng thường có nghĩa là mỗi thay đổi sẽ chạy lại pipeline trên một tập dữ liệu nhỏ, để một bước bị hỏng được phát hiện trước khi nó đi vào một phân tích lớn hơn. Một tác dụng phụ hữu ích là một máy mới — hoặc một máy chủ đã bị xoá — có thể dựng lại và chạy lại công việc chỉ từ kho lưu trữ.

## Các lệnh Git

Kho ví dụ được commit theo từng bước. Clone kho và checkout các nhánh là một cách để theo dõi quá trình phát triển.

```bash
# clone
git clone git@github.com:nttg8100/ngs-quality-control-for-blog-example.git
cd ngs-quality-control-for-blog-example

# checkout to branch for the relevant tutorial step, e.g. feature/add-data
git checkout feature/add-data
```

:::tip
+ Để thoát trình phân trang của `git log`, gõ `q`
+ Tạo kho riêng của bạn sẽ cho một bài thực hành thực tế hơn
+ So sánh các tệp với kho ví dụ, rồi sao chép những phần cần thiết vào kho của bạn
:::

### Cách checkout một commit cụ thể

Chỉ cần dùng mã hash của commit là đủ. Ví dụ, để xem tất cả tệp từ commit `230795b`:

```bash
git checkout 230795b
```

Trình soạn thảo sau đó hiển thị các tệp đúng như ở commit đó.

### Cách khôi phục

Nếu đã checkout một commit và thực hiện vài thay đổi để thử nghiệm, `git` sẽ yêu cầu commit chúng trước khi chuyển nhánh. Khôi phục về bản gốc khá đơn giản:

```bash
git checkout -- .
```

Đôi khi chỉ cần một tệp từ một nhánh khác:

```bash
git checkout <branch name> <relative file path>
# ex: git checkout main .gitignore
```

## Thêm dữ liệu

Tạo một nhánh mới từ `main` đã cập nhật:

```bash
git checkout main
git pull origin main
git switch -c feature/add-data
```

Giờ ta thêm vài target vào Makefile để tự động hoá việc tải dữ liệu và dọn dẹp:

- **Target `data`**: tải các tệp FASTQ ví dụ vào thư mục `data/GSE110004`. Mọi người trong dự án sau đó dùng cùng một dữ liệu đầu vào.
- **Target `clean`**: xoá thư mục đã tải, giúp đặt lại môi trường hoặc giải phóng dung lượng đĩa.

`Makefile` đã cập nhật:

```Makefile
${HOME}/.pixi/bin/pixi:
	mkdir -p ${HOME}/.pixi/bin
	curl -sSL https://pixi.sh/install.sh | sh

data:
	mkdir -p data/GSE110004
	wget -O data/GSE110004/SRR6351937_1.fastq.gz https://ftp.sra.ebi.ac.uk/vol1/fastq/SRR635/007/SRR6351937/SRR6351937_1.fastq.gz
	wget -O data/GSE110004/SRR6351937_2.fastq.gz https://ftp.sra.ebi.ac.uk/vol1/fastq/SRR635/007/SRR6351937/SRR6351937_2.fastq.gz

clean:
	rm -rf data
```

Theo cùng quy trình như ở Phần 1, commit, push, mở pull request và merge vào `main`:

```bash
git commit -m "feat: add makefile to get data"
git push origin feature/add-data
```

## Thêm workflow

Tạo một nhánh khác:

```bash
git checkout main
```

### Thêm script workflow `main.sh` và kiểm thử

Script dưới đây chạy FastQC và MultiQC cho một mẫu paired-end, nhận đầu vào qua tham số dòng lệnh.

```bash
# create workflow file using bash script, this runs for only paired reads of 1 sample
cat << EOF >> main.sh
#!/bin/bash

# Usage: ./main.sh <read1.fastq.gz> <read2.fastq.gz> <output_folder>

set -e

if [ "\$#" -ne 3 ]; then
    echo "Usage: $0 <read1.fastq.gz> <read2.fastq.gz> <output_folder>"
    exit 1
fi

READ1="\$1"
READ2="\$2"
OUTDIR="\$3"

mkdir -p "\$OUTDIR"

echo "Running FastQC on \$READ1 and \$READ2..."
fastqc "\$READ1" "\$READ2" -o "\$OUTDIR"

echo "Running MultiQC in \$OUTDIR..."
multiqc "\$OUTDIR" -o "\$OUTDIR"

echo "All done. Results are in \$OUTDIR"
EOF

# chmod to be executed
chmod +x main.sh

# get help script
bash main.sh
# Usage: main.sh <read1.fastq.gz> <read2.fastq.gz> <output_folder>

# test it with your data
# activate pixi
pixi shell
# run interactively
bash main.sh data/GSE110004/*_1.fastq.gz data/GSE110004/*_2.fastq.gz result

# run with pixi directly
pixi run bash main.sh data/GSE110004/*_1.fastq.gz data/GSE110004/*_2.fastq.gz result
```

### Dùng Makefile để thêm kiểm thử

Sau đó có thể chạy kiểm thử thông qua Makefile:

```Makefile
.PHONY: install-pixi test-e2e clean
${HOME}/.pixi/bin/pixi:
	mkdir -p ${HOME}/.pixi/bin
	curl -sSL https://pixi.sh/install.sh | sh

data/GSE110004:
	mkdir -p data/GSE110004
	cd data/GSE110004 && \
	wget https://raw.githubusercontent.com/nf-core/test-datasets/rnaseq/testdata/GSE110004/SRR6357070_1.fastq.gz && \
	wget https://raw.githubusercontent.com/nf-core/test-datasets/rnaseq/testdata/GSE110004/SRR6357070_2.fastq.gz

test-e2e: data/GSE110004
	${HOME}/.pixi/bin/pixi run bash main.sh data/GSE110004/*_1.fastq.gz data/GSE110004/*_2.fastq.gz result

clean:
	rm -rf data/GSE110004
```

Chạy kiểm thử:

```bash
make test-e2e
```

Thêm kết quả sinh ra vào `.gitignore` để chúng không bị commit:

```bash
# Build and Release Folders
bin-debug/
bin-release/
[Oo]bj/
[Bb]in/

# Other files and folders
.settings/

# Executables
*.swf
*.air
*.ipa
*.apk

# Project files, i.e. `.project`, `.actionScriptProperties` and `.flexProperties`
# should NOT be excluded as they contain compiler settings and other important
# information for Eclipse / Flash Builder.
# pixi environments
.pixi/*
!.pixi/config.toml
data
result
```

Commit, push, mở pull request và merge vào `main` như trước:

```bash
git add .
git commit -m "feat: add workflow"
git push origin feature/workflow
```

Sau đó, từ thư mục gốc của kho, tải và kiểm tra dữ liệu:

:::tip
+ Các target make hiện khá đơn giản và có thể chạy trực tiếp. Khi dự án lớn hơn, nên mở rộng chúng, ví dụ để `make clean` xoá thêm nhiều tệp và thư mục hơn.
:::

```bash
git checkout
# download data
make data
# test that data is downloaded
ls -lah  data/GSE110004
# total 4.3M
# drwxrwxr-x 2 <user> <group> 4.0K Jan 19 01:00 .
# drwxrwxr-x 3 <user> <group> 4.0K Jan 19 01:00 ..
# -rw-rw-r-- 1 <user> <group> 2.2M Jan 19 01:00 SRR6357070_1.fastq.gz
# -rw-rw-r-- 1 <user> <group> 2.2M Jan 19 01:00 SRR6357070_2.fastq.gz

# delete data folder
make clean
```

## Cấu hình kiểm thử

Tới đây mọi thứ đều được làm cục bộ. Khi thêm một tính năng mới — ví dụ thêm `trimmomatic` để cắt tỉa các read — cần chạy lại kiểm thử để xác nhận pipeline vẫn hoàn tất mà không có lỗi. Đây là dạng kiểm thử đơn giản nhất cho một dự án bioinformatics.

GitHub Actions là một dịch vụ có thể chạy kiểm thử này tự động:

:::info
+ Quickstart chính thức trình bày GitHub Actions chi tiết hơn: https://docs.github.com/en/actions/get-started/quickstart
+ Ở đây chúng ta chỉ giới thiệu cách nó hoạt động và cách áp dụng cho một dự án nhỏ
:::

### Tạo các tệp GitHub Actions

Tạo một nhánh cho CI/CD:

```bash
git checkout main
git pull
git switch -c feature/cicd
```

Sau đó tạo workflow:

```bash
mkdir -p .github/workflows
# create workflow file
cat << EOF >> .github/workflows/test-e2e.yaml
name: Testing e2e

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  clone:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout repository
        uses: actions/checkout@v4

      - name: Running testing
        run: |
          make test-e2e
EOF
```

Workflow này làm những việc sau:

+ chạy một workflow tên `Testing e2e`
+ kích hoạt khi có pull request vào `main`
+ kích hoạt khi push hoặc merge vào `main`
+ khởi động một job trên runner `ubuntu-latest`
+ clone kho bằng `actions/checkout`
+ chạy kiểm thử end-to-end qua `make test-e2e`
+ đạt nếu kiểm thử thành công, và thất bại nếu chúng trả về mã thoát khác 0

### Chạy GitHub Actions cục bộ

Nếu chỉ chạy kiểm thử khi mở pull request hoặc push lên `main`, có thể cần vài commit nhỏ chỉ để kích hoạt kiểm thử. `act` là một công cụ dòng lệnh cục bộ chạy một workflow GitHub Actions ngay trên máy, giúp rút ngắn vòng lặp đó:

:::info
+ Chi tiết thêm về `act` tại https://nektosact.com
+ Cài Docker trên máy cục bộ trước
:::

```bash
# install
pixi add act
# run e2e test locally, it will run this on your local machine
act -W .github/workflows/test-e2e.yaml
```

![act_failed](./imgs/act_failed.png)

:::warning
Như log cho thấy, lần chạy thất bại vì `pixi` chưa được cài: target `make test-e2e` không phụ thuộc vào target cài đặt Pixi. Makefile ở commit trước cũng trỏ tới một URL cài đặt đã cũ (`https://pixi.dev/install.sh`); trình cài đặt hiện tại là `https://pixi.sh/install.sh`. Thêm cài đặt Pixi làm phụ thuộc của `test-e2e` sẽ khắc phục lỗi này.

Cập nhật phụ thuộc của `test-e2e` trong `Makefile`:

```Makefile
test-e2e: data/GSE110004 ${HOME}/.pixi/bin/pixi
	${HOME}/.pixi/bin/pixi run bash main.sh data/GSE110004/*_1.fastq.gz data/GSE110004/*_2.fastq.gz result

	rm -rf data/GSE110004
```

## CI/CD trong bioinformatics là gì?

### Trong phát triển phần mềm

![cicd](./imgs/cicd.webp)

CI (continuous integration) và CD (continuous delivery/deployment) là những thuật ngữ phổ biến trong phát triển phần mềm. Trong sơ đồ trên, quá trình phát triển phần mềm đi qua nhiều tính năng mới, mỗi tính năng kích hoạt một tập job. Trong ví dụ ở đây, workflow clone kho trên một runner của GitHub Actions và chạy kiểm thử. Các job cụ thể phụ thuộc vào use case của dự án.

### Trong bioinformatics

Một dự án bioinformatics phát triển phần mềm đi theo cùng quy trình CI/CD chung. Thường gặp hơn, bioinformatics kết hợp các công cụ sẵn có: các script (bash, Nextflow, WDL, Snakemake, v.v.) nối công cụ lại thành một workflow. Trong bối cảnh đó, bản phát hành thường chính là kho lưu trữ cùng các script bên trong (CD), còn CI là pipeline chạy trên một tập dữ liệu kiểm thử.

Khi workflow đã có, việc mở một pull request sẽ kích hoạt kiểm thử, và kết quả cho biết thay đổi có khả năng làm hỏng pipeline hay không:

![PR_GHA](./imgs/PR_GHA.png)

:::tip
+ Dùng secrets trong `Settings` cho thông tin xác thực (mật khẩu, tên đăng nhập, khoá)
+ Giữ Makefile và môi trường GitHub Actions đồng bộ giúp việc đổi runner CI/CD dễ hơn
+ Chiến lược matrix có thể chạy kiểm thử nhanh hơn
:::

## Tổng kết

Bài hướng dẫn này đã đưa một dự án bioinformatics nhỏ thành một pipeline tái lập và có thể kiểm thử, dùng Git, Makefile và GitHub Actions. Các điểm chính:

### Các lệnh Git cho quản lý dự án
- `git log` và `git log --oneline` hiển thị lịch sử commit
- checkout một commit cụ thể cho phép xem lại một trạng thái trước đó
- `git diff` so sánh cây làm việc với một commit, hoặc hai commit với nhau
- `git checkout -- .` khôi phục cây làm việc
- `git checkout <branch> <file>` sao chép một tệp từ nhánh khác

### Tự động hoá bằng Makefile
- các target tải dữ liệu (`make data`) và dọn dẹp (`make clean`)
- một target kiểm thử (`make test-e2e`) nối các phụ thuộc của nó
- các lệnh được chuẩn hoá giúp môi trường dễ so sánh hơn

### Script workflow
- script bash có thể nhận tham số dòng lệnh
- các công cụ như FastQC và MultiQC có thể được kết hợp trong một script
- có thể kiểm thử script cục bộ trước khi push

### CI/CD với GitHub Actions
- các tệp workflow nằm trong `.github/workflows/`
- có thể kích hoạt kiểm thử khi push lên `main` hoặc khi có pull request
- dùng cùng các lệnh Makefile ở cục bộ và trong CI
- log của Actions dùng để gỡ lỗi khi một lần chạy thất bại

### Kiểm thử cục bộ với `act`
- `act` chạy một workflow GitHub Actions ngay trên máy
- có thể phát hiện vấn đề trước khi push
- thường cần ít commit hơn để sửa một lỗi CI

### CI/CD trong bối cảnh bioinformatics
- khác với phần mềm thông thường, trọng tâm thường là kiểm định pipeline
- "delivery" thường chính là kho lưu trữ cùng các workflow tái lập của nó
- kiểm thử thường có nghĩa là chạy toàn bộ pipeline trên một tập dữ liệu kiểm thử
- đây là một cách để phát hiện thay đổi làm hỏng các phân tích đang có

Một dự án được tổ chức theo cách này dễ tái lập trên máy khác, dễ kiểm thử tự động và dễ bảo trì theo thời gian hơn.
