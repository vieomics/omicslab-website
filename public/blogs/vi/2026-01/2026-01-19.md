Amazon S3 (Simple Storage Service) lưu file dưới dạng object, mỗi object được định danh bằng một key duy nhất thay vì một đường dẫn trong hệ thống file truyền thống. Thiết kế này mở rộng tốt cho lưu trữ, nhưng có thể gây trở ngại khi dùng S3 như một hệ thống file thông thường, đặc biệt trong các workflow bioinformatics. Khi Nextflow dùng S3 làm backend input/output, có những đánh đổi cần cân nhắc, nhất là với số lượng lớn file nhỏ. Trong những trường hợp đó, Nextflow có thể dành đáng kể thời gian cho việc tải lên và tải xuống qua AWS CLI v2, ảnh hưởng đến hiệu năng tổng thể của workflow. Bài này bắt đầu từ phía input.

<!--truncate-->

## AWS CLI

### Cài đặt

AWS CLI là công cụ dòng lệnh để làm việc với các dịch vụ AWS. Trong Nextflow, nó có thể dùng để tải input xuống và tải output lên. Để làm theo hướng dẫn, hãy clone repository. Repository dùng pixi và Docker để thiết lập môi trường nhanh.

```bash
git clone https://github.com/nttg8100/nextflow-cost-optimization.git
cd nextflow-cost-optimization
pixi shell
which aws
```

`Makefile` dưới đây khởi động dịch vụ Docker, tải các file lên, và tạo một tar archive gồm 10.000 file nhỏ để dùng cho benchmark về sau.

```bash
aws-config: start-minio
	export AWS_ACCESS_KEY_ID="minioadmin"; \
	export AWS_SECRET_ACCESS_KEY="minioadmin"; \
	export AWS_DEFAULT_REGION="us-east-1"; \
	export AWS_ENDPOINT_URL="http://localhost:9000" ; \
	sleep 10 && aws s3 mb s3://io-benchmark --endpoint-url http://localhost:9000

results/tarball.tar:
	@mkdir -p results/tarball
	@count=10000; size=1M; index=1; \
	for k in $$(seq $$count); do \
		dd if=/dev/zero of=results/tarball/$${size}-$${index}-$$k.data bs=1 count=0 seek=$$size; \
	done
	tar -cvf results/tarball.tar -C results/tarball .

upload-tar:
	aws s3 cp results/tarball.tar s3://io-benchmark/ --endpoint-url http://localhost:9000

upload-10k-files:
	aws s3 cp results/tarball  s3://io-benchmark/tarball --endpoint-url http://localhost:9000 --recursive
```

### Khởi động dịch vụ S3

Đến đây bạn có thể làm việc với S3 object storage. Lệnh này khởi chạy MinIO, một dịch vụ tương thích S3, giúp giảm lỗi phát sinh từ khác biệt giữa máy cục bộ và bucket từ xa. Nó tạo bucket tên `io-benchmark` và đồng thời sinh ra nhiều file nhỏ dùng về sau để minh hoạ vấn đề.

```bash
make aws-config
```

Để kiểm tra dịch vụ S3:

```bash
# export env
export AWS_ACCESS_KEY_ID="minioadmin"
export AWS_SECRET_ACCESS_KEY="minioadmin"
export AWS_DEFAULT_REGION="us-east-1"
export AWS_ENDPOINT_URL="http://localhost:9000"
# configure threads
aws configure set default.s3.max_concurrent_requests 8
# test bucket
aws s3 ls  --endpoint-url http://localhost:9000
```

### Kiểm tra tải xuống độc lập

`Makefile` ở trên tạo một thư mục gồm 10.000 file, mỗi file 1 MB, cùng một tar archive của chính các file đó. Nextflow có thể chậm với input vì hai lý do chính:

+ Nó kiểm tra (verify) việc tải xuống của từng file
+ Nó tính toán input cache cho tất cả file nhỏ

:::tip
`Makefile` cũng tạo một file tar của 10.000 file này. Benchmark dưới đây cho thấy vì sao điều này quan trọng và nó có thể giúp workflow dễ hơn như thế nào.
:::

Trước khi liên quan đến Nextflow, hãy đo thời gian thao tác này chỉ với AWS CLI v2.

#### Hệ thống dựa trên FUSE

Ngoài việc tải từng file hoặc file tar bằng lệnh `aws`, một hệ thống dựa trên FUSE là cách tiếp cận thay thế.

:::tip
+ Với file nhỏ: FUSE cho phép ứng dụng truy cập từng file theo nhu cầu mà không cần tải toàn bộ archive hay dùng lệnh phức tạp, giúp giảm overhead và truy cập nhanh, tiện.
+ Với file lớn: filesystem FUSE có thể chỉ lấy các chunk dữ liệu cần thiết, cho phép đọc một phần hiệu quả, stream tuần tự, và tránh việc tải toàn bộ không cần thiết.
+ Lợi ích chung: vì FUSE đưa cloud storage ra như một cây thư mục tiêu chuẩn, các workflow và công cụ vốn dùng file cục bộ hoạt động theo cùng cách, cho phép truy cập song song và tích hợp với caching và prefetching.
:::

Cách này hữu ích cho những ứng dụng làm việc với một file lớn, hoặc một thư mục chứa nhiều file nhỏ, nhưng không nạp toàn bộ. Ví dụ, khi annotate biến thể cho dữ liệu whole-exome, cơ sở dữ liệu annotation được xây cho toàn bộ hệ gen; một FUSE mount cho phép công cụ chỉ đọc các vùng cần cho những biến thể được annotate. Các engine phân tán dùng hệ thống dựa trên FUSE cũng có thể hưởng lợi từ việc nạp dữ liệu theo nhu cầu.

`Makefile` dưới đây cài `mount-s3` qua pixi. Nó mount toàn bộ bucket tại `/mnt/vep_cache`. Điểm mount được đặt tên theo `vep` vì nó được dùng ở ví dụ annotate VEP về sau.

```bash
mount-s3-vep-cache: ${HOME}/.pixi/bin/pixi
	mkdir -p ./mnt/vep_cache
	mkdir -p ./mnt/tmp
	${HOME}/.pixi/bin/pixi run -e mount mount-s3 --endpoint-url http://localhost:9000 --region us-east-1 --force-path-style io-benchmark ./mnt/vep_cache --read-only --cache ./mnt/tmp --max-threads 8
```

Chạy lệnh này để mount bucket S3 từ xa:

```bash
make mount-s3-vep-cache
# check

# Filesystem                            1K-blocks      Used     Available Use% Mounted on
# io-benchmark                      1099511627776         0 1099511627776   0% /scratch/data/nextflow-cost-optimization/mnt/vep_cache
```

Khi đã mount, có thể copy 10.000 file về cục bộ:

```bash
for i in {1..3}; do /usr/bin/time -f "%e" bash -c 'cp -r ./mnt/vep_cache/tarball tarball ' 2>&1 | tail -n 1; rm -rf ./tarball; done
```

Cũng có thể đọc một file tar duy nhất qua mount:

```bash
for i in {1..3}; do /usr/bin/time -f "%e" bash -c 'mkdir -p tarball && cp ./mnt/vep_cache/tarball.tar tarball' 2>&1 | tail -n 1; rm -rf ./tarball; done
```

### Tóm tắt

Bảng dưới đây tóm tắt các cách tải 10.000 file nhỏ từ S3, với hiệu năng quan sát được và trường hợp sử dụng điển hình:

| Method                                 | Download Time (s) | Pros                                    | Cons                                 | When to Use                                    |
| -------------------------------------- | ----------------- | --------------------------------------- | ------------------------------------ | ---------------------------------------------- |
| **AWS CLI (recursive, 10k files)**     | ~110              | Simple, no extra setup                  | Very slow for many small files       | Rarely; only for small numbers of files        |
| **AWS CLI (tarball + untar via pipe)** | ~33               | Fast, single download + extraction      | Needs tar/untar logic                | When workflow can handle tar extraction        |
| **FUSE (cp -r 10k files)**             | ~45               | Transparent, works like local FS        | Needs FUSE setup, not always fastest | When random access or partial reads are needed |
| **FUSE (cat tarball \| tar -xvf -)**   | ~20               | Fast, combines FUSE and streaming untar | Needs FUSE setup, tar logic          | For large archives with extraction             |

:::info
**Khuyến nghị:**
- Với nhiều file nhỏ, tránh tải đệ quy trực tiếp; dùng tarball hoặc giải pháp dựa trên FUSE.
- Dùng tarball + untar (qua pipe) để có hiệu năng tốt nhất nếu có thể gộp file.
- FUSE phù hợp với workflow cần truy cập ngẫu nhiên hoặc đọc một phần, hoặc khi không thể thay đổi cấu trúc file.
- Nextflow (v25.04+) được báo cáo là cải thiện xử lý file nhỏ, nhưng gộp file hoặc dùng FUSE vẫn mang lại lợi ích khi số file lớn.
:::

## Tích hợp Nextflow

### Workflow

Workflow dưới đây nhận input từ S3, tải về để dùng trong process, và đếm số file bên trong.

```bash
include { COUNT_FILES }  from './modules/count_files_tar.nf'
include { COUNT_FILES_TAR } from './modules/count_files_tar.nf'

workflow {
    main:        
        // benchmark files input
        // normal files
        if (params.benchmark_input){
            ch_files = COUNT_FILES(Channel.fromPath(params.inputs).collect())
        }

        // tarball and untar
        if (params.benchmark_input_tar){
            ch_files = COUNT_FILES_TAR(Channel.fromPath(params.inputs).collect())
        }
}
```

### Các module

#### COUNT_FILES

Nó nhận danh sách file trực tiếp từ S3.

```bash
process COUNT_FILES {
    cpus 2

    input:
    path(file_path)

    script:
    """
    ls -lah tarball/**.data|wc -l > num_files.txt
    """
}
```

#### COUNT_FILES_TAR

Nó tải file tar trước, rồi giải nén bên trong process.

:::info
Việc tải file và dùng pipe để giải nén nhanh được áp dụng về sau.
:::

```bash
process COUNT_FILES_ {
    cpus 2

    input:
    path(file_path)

    script:
    """
    tar -xf ${file_path}
    ls -lah tarball/**.data|wc -l > num_files.txt
    """
}
```

### Cải thiện chỉ bằng cấu hình

Chúng tôi đã cho thấy có thể dùng một file tar lớn làm input và giải nén bên trong process. Điều đó đòi hỏi phải thay đổi module. Vậy có cấu hình nào tránh được việc đó không? Tiếp nối cách dùng pipe ở trên, cấu hình dưới đây giữ nguyên module trong khi các file được nạp bằng `beforeScript`.

```bash
process{
    withName:COUNT_FILES{
        beforeScript = "mkdir -p tarball && aws s3 cp s3://io-benchmark/tarball.tar - --endpoint-url http://localhost:9000 | tar -xvf - -C tarball"
    }
}
```

Để chạy workflow, có thể dùng một file làm placeholder cho Nextflow nhận input, và thêm cấu hình `nextflow_tar.config`:

```Makefile
test-input-tar-pipe: ${HOME}/.pixi/bin/pixi
	${HOME}/.pixi/bin/pixi run -e standard nextflow run benchmark_input.nf \
		-c nextflow_s3.config -c nextflow_tar.config \
		--benchmark_input \
		--inputs="s3://io-benchmark/tmp.txt"
```

Nhớ tạo file tạm và tải lên bucket:

```bash
touch tmp.txt
aws s3 cp tmp.txt  s3://io-benchmark --endpoint-url http://localhost:9000 
```

Chạy thiết lập mới:

```bash
time make test-input-tar-pipe
# 11,33s user 2,85s system 82% cpu 17,166 total
```

## Case study Genomics England

Tham khảo: **https://aws.amazon.com/blogs/hpc/optimize-nextflow-workflows-on-aws-batch-with-mountpoint-for-amazon-s3/**

### Vấn đề

Mô hình tương tự cũng xuất hiện trong workload thực tế. Bài viết trên blog AWS HPC mô tả cách Genomics England xử lý một vấn đề tương tự khi dùng VEP để annotate biến thể. Cơ sở dữ liệu họ dùng chứa nhiều file nhỏ, và việc tải xuống mất nhiều thời gian hơn cả bước annotation, vốn chỉ chạy trong vài phút.

Pseudo code:

```bash
process VEP {

    input:
    path(vcf)
    val(vep_cache)

    script:
    """
    vep \
        --input_file $vcf \
        --fasta $params.human_reference_fasta \
        --dir_cache $vep_cache 
    """

}
```

### Workflow và module

Workflow chỉ dùng module VEP. Để tái lập nhanh, mọi tham số đều được hard code.

```bash
include { ENSEMBLVEP_VEP } from './modules/vep.nf'

workflow {
    main:
        ENSEMBLVEP_VEP(
            Channel.of(tuple([id: 'HCC1395N'], file("inputs/vep_test_data.vcf.gz"), file("inputs/vep_test_data.vcf.gz.tbi"))), // tuple val(meta), path(vcf), path(custom_extra_files)
            Channel.value("GRCh38"), // val genome
            Channel.value("homo_sapiens"), // val species
            Channel.value(114), // val cache_version
            Channel.fromPath("s3://io-benchmark/vep_cache"), // path cache
            Channel.of(tuple([:], [])), // tuple val(meta2), path(fasta)
            Channel.of([]) // path extra_files
        )
}
```

Module VEP được lấy từ [**nf-core**](https://github.com/nf-core/sarek/blob/20f41d1ce8b7ba296ee22adc71fe2da2ebcae93f/modules/nf-core/ensemblvep/vep/main.nf).

```bash
process ENSEMBLVEP_VEP {
    tag "${meta.id}"
    label 'process_medium'

    conda "${moduleDir}/environment.yml"
    container "${workflow.containerEngine == 'singularity' && !task.ext.singularity_pull_docker_container
        ? 'https://community-cr-prod.seqera.io/docker/registry/v2/blobs/sha256/4b/4b5a8c173dc9beaa93effec76b99687fc926b1bd7be47df5d6ce19d7d6b4d6b7/data'
        : 'community.wave.seqera.io/library/ensembl-vep:115.2--90ec797ecb088e9a'}"

    input:
    tuple val(meta), path(vcf), path(custom_extra_files)
    val genome
    val species
    val cache_version
    path cache
    tuple val(meta2), path(fasta)
    path extra_files

    output:
    tuple val(meta), path("*.vcf.gz"), emit: vcf, optional: true
    tuple val(meta), path("*.vcf.gz.tbi"), emit: tbi, optional: true
    tuple val(meta), path("*.tab.gz"), emit: tab, optional: true
    tuple val(meta), path("*.json.gz"), emit: json, optional: true
    path "*.html", emit: report, optional: true
    path "versions.yml", emit: versions

    when:
    task.ext.when == null || task.ext.when

    script:
    def args = task.ext.args ?: ''
    def args2 = task.ext.args2 ?: ''
    def file_extension = args.contains("--vcf") ? 'vcf' : args.contains("--json") ? 'json' : args.contains("--tab") ? 'tab' : 'vcf'
    def compress_cmd = args.contains("--compress_output") ? '' : '--compress_output bgzip'
    def prefix = task.ext.prefix ?: "${meta.id}"
    def dir_cache = cache ? "\${PWD}/${cache}" : "/.vep"
    def reference = fasta ? "--fasta ${fasta}" : ""
    def create_index = file_extension == "vcf" ? "tabix ${args2} ${prefix}.${file_extension}.gz" : ""
    """
    vep \\
        -i ${vcf} \\
        -o ${prefix}.${file_extension}.gz \\
        ${args} \\
        ${compress_cmd} \\
        ${reference} \\
        --assembly ${genome} \\
        --species ${species} \\
        --cache \\
        --cache_version ${cache_version} \\
        --dir_cache ${dir_cache} \\
        --fork ${task.cpus}

    ${create_index}

    cat <<-END_VERSIONS > versions.yml
    "${task.process}":
        ensemblvep: \$( echo \$(vep --help 2>&1) | sed 's/^.*Versions:.*ensembl-vep : //;s/ .*\$//')
        tabix: \$(echo \$(tabix -h 2>&1) | sed 's/^.*Version: //; s/ .*\$//')
    END_VERSIONS
    """

    stub:
    def prefix = task.ext.prefix ?: "${meta.id}"
    def file_extension = args.contains("--vcf") ? 'vcf' : args.contains("--json") ? 'json' : args.contains("--tab") ? 'tab' : 'vcf'
    def create_index = file_extension == "vcf" ? "touch ${prefix}.${file_extension}.gz.tbi" : ""
    """
    echo "" | gzip > ${prefix}.${file_extension}.gz
    ${create_index}
    touch ${prefix}_summary.html

    cat <<-END_VERSIONS > versions.yml
    "${task.process}":
        ensemblvep: \$( echo \$(vep --help 2>&1) | sed 's/^.*Versions:.*ensembl-vep : //;s/ .*\$//')
        tabix: \$(echo \$(tabix -h 2>&1) | sed 's/^.*Version: //; s/ .*\$//')
    END_VERSIONS
    """
}
```

Giải pháp của họ được trình bày dưới đây.

### Input

File VCF được chuẩn bị trong thư mục `inputs`, còn cơ sở dữ liệu cache VEP có thể được chuẩn bị qua `Makefile` dưới đây.

```bash

vep/114_GRCh38: ${HOME}/.pixi/bin/pixi
	mkdir -p vep
	touch vep/vep_cache
	cd vep && ${HOME}/.pixi/bin/pixi run -e core aws s3 --no-sign-request cp s3://annotation-cache/vep_cache/114_GRCh38 114_GRCh38 --recursive

vep/vep_cache.tar: vep/114_GRCh38
	tar -cvf vep/vep_cache.tar -C vep/114_GRCh38 .

upload-vep-cache: vep/vep_cache.tar
	${HOME}/.pixi/bin/pixi run -e core aws s3 cp vep/114_GRCh38 s3://io-benchmark/ --endpoint-url http://localhost:9000 --recursive
	${HOME}/.pixi/bin/pixi run -e core aws s3 cp vep/vep_cache.tar s3://io-benchmark/ --endpoint-url http://localhost:9000
	
mount-s3-vep-cache: ${HOME}/.pixi/bin/pixi
	mkdir -p ./mnt/vep_cache
	mkdir -p ./mnt/tmp
	${HOME}/.pixi/bin/pixi run -e mount mount-s3 --endpoint-url http://localhost:9000 --region us-east-1 --force-path-style io-benchmark ./mnt/vep_cache --read-only --cache ./mnt/tmp --max-threads 8
```

Sau đó chạy:

```bash
# download and upload to local s3
make upload-vep-cache

# mount to local folder from local s3 via mountpoint-s3 
make mount-s3-vep-cache
```

Các lệnh `Makefile` dưới đây benchmark nhanh các phương án:

```bash
test-vep-local: ${HOME}/.pixi/bin/pixi
	${HOME}/.pixi/bin/pixi run -e core nextflow run benchmark_vep.nf -profile docker --vep_cache "./vep/114_GRCh38"

test-vep-mount-cache: ${HOME}/.pixi/bin/pixi
	${HOME}/.pixi/bin/pixi run -e core nextflow run benchmark_vep.nf \
		-c nextflow_s3.config -c nextflow_vep_mount.config --vep_cache "./mnt/vep_cache/114_GRCh38" -profile docker

test-vep-direct-s3: ${HOME}/.pixi/bin/pixi
	${HOME}/.pixi/bin/pixi run -e core  nextflow run benchmark_vep.nf \
		-c nextflow_s3.config --vep_cache "s3://io-benchmark/114_GRCh38" -profile docker

test-vep-tar-cache: ${HOME}/.pixi/bin/pixi
	${HOME}/.pixi/bin/pixi run -e core nextflow run benchmark_vep.nf \
		-c nextflow_s3.config -c nextflow_vep_tar.config --vep_cache "s3://io-benchmark/vep_cache" -profile docker

test-vep-mount-tar: ${HOME}/.pixi/bin/pixi
	${HOME}/.pixi/bin/pixi run -e core nextflow run benchmark_vep.nf \
		-c nextflow_s3.config -c nextflow_vep_mount_tar.config --vep_cache "s3://io-benchmark/vep_cache" -profile docker
```

Sau đó chạy ví dụ cần kiểm tra:

```bash
make <test-vep-benchmark>
```

Bảng dưới đây tóm tắt kết quả benchmark của các cách truy cập cơ sở dữ liệu cache VEP trong quá trình phân tích:

| Method              | Command                     | Time (min:sec) |
| ------------------- | --------------------------- | :------------: |
| Local cache         | `make test-vep-local`       |    2:26.20     |
| S3 mount (FUSE)     | `make test-vep-mount-cache` |    2:31.08     |
| S3 mount tar (FUSE) | `make test-vep-mount-tar`   |    5:57.18     |
| Direct S3 access    | `make test-vep-direct-s3`   |    6:32.63     |
| S3 tar cache        | `make test-vep-tar-cache`   |    6:02.52     |

:::info
+ Như đã nêu ở trên, không cần tải toàn bộ cơ sở dữ liệu cache để annotate một file VCF vùng nhỏ. Đó là lý do mount toàn bộ cơ sở dữ liệu là phương án nhanh nhất trong trường hợp này.
+ Thay lệnh VEP bằng `cp \$(readlink $cache) tmp -r` trong module cho thấy mất `4:16.09` để đọc từ điểm mount và copy toàn bộ thư mục sang một thư mục tạm mới.
+ Tuỳ vào hạ tầng cụ thể của bạn, hãy điều chỉnh các lựa chọn này cho phù hợp.
:::

### Tóm tắt

+ Dùng file tar và giải nén input lớn không phải lúc nào cũng đảm bảo cải thiện hiệu năng đáng kể. Lợi ích phụ thuộc vào số lượng file và tổng kích thước thư mục input.
+ Nếu công cụ chỉ truy cập một phần các file input (thay vì toàn bộ thư mục), hiệu năng có thể tương đương với việc cơ sở dữ liệu đã có sẵn cục bộ.

## Tóm tắt chung

### Phân tích hiệu năng

- **File nhỏ so với file lớn**: Nextflow xử lý file lớn đơn lẻ hiệu quả nhưng chậm hơn với nhiều file nhỏ do phải thao tác trên từng file.
- **Các phương thức tải**: với tập file nhỏ này, dùng file tar nhanh hơn đáng kể so với tải đệ quy.
- **Lợi ích của FUSE**: mount point cho phép truy cập trong suốt với hiệu năng tốt và không cần dung lượng đĩa cục bộ cho toàn bộ dữ liệu.

### Chiến lược tối ưu

- **Gộp file nhỏ**: dùng tar archive khi phải xử lý nhiều file (10k+ file nhỏ).
- **Stream processing**: pipe giải nén để xử lý ngay mà không cần tải toàn bộ.
- **Caching**: dùng caching dựa trên FUSE cho cơ sở dữ liệu và dữ liệu tham chiếu.
- **Chọn đúng phương thức**: chọn cách tải theo số lượng file và kiểu truy cập.

### Ứng dụng thực tế

- **Case study Genomics England**: annotate VEP dựa trên FUSE.
- **Các pipeline bioinformatics**: các nguyên tắc áp dụng cho bất kỳ workflow nào dùng lưu trữ dữ liệu từ xa.
- **Cân nhắc chi phí**: giảm thời gian tải và giảm dung lượng đĩa giúp giảm chi phí tính toán trên các nền tảng cloud.

### Những điểm chính

1. **Đo trước khi tối ưu**: hãy đo điểm nghẽn thực tế trong workflow cụ thể của bạn.
2. **Cân nhắc phân bố file**: nhiều file nhỏ không giống vài file lớn khi chọn chiến lược tải.
3. **Cân nhắc Nextflow v25.04+**: cải thiện được báo cáo cho xử lý file nhỏ giúp giảm nhu cầu dùng workaround.
4. **Dùng FUSE khi phù hợp**: nó có thể cho truy cập trong suốt với hiệu năng tốt hơn công cụ CLI.
5. **Thiết kế để mở rộng**: xây workflow hoạt động hiệu quả với đặc điểm dữ liệu của bạn.

Dù dữ liệu là hàng nghìn file nhỏ hay hàng terabyte dữ liệu tham chiếu, những mô hình này giúp thiết kế workflow dùng input hiệu quả hơn.
